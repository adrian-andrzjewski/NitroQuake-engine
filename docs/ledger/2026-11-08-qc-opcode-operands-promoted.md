# QuakeC opcode-local operand resolution (2026-11-08)

## Change and invariant

`PR_ExecuteProgram` resolves A/B/C pointers in each opcode group instead of
unconditionally resolving all three before dispatch. Return/goto instructions
need no such pointers; calls/conditions and stores consume fewer operands than
arithmetic/vector instructions. Signed branch displacements are not global offsets.

All arithmetic expressions, statement/profile increments, trace behavior, calls,
return handling and error checks remain. No opcode is approximated, removed or
predecoded into an additional table. There is no new runtime state or allocation.

## Generated code and correctness

Control source is `fd2b7a5`. Across 435 normalized C/H/S/INC files, only pr_exec.c
differs. Its source SHA-256 is
`e19a3c3a2fe33956adfad2d726a87d71bc5a1dae47d9090d39588e68d786baa1`.

GCC 12.2 i486 output removes six eager operand-setup instructions from the common
header, keeps the runaway counter in a register and reduces stack locals from
44 to 28 bytes. Required operands still need resolution in their cases. The
pr_exec object text grows from 0x12e0 to 0x15e0, a 768-byte instruction-footprint
tradeoff; no physical instruction-cache benefit is asserted.

The native differential fixture passed 11,076 cases under the retained fast-math
build: all 66 opcodes, ten input/alias variants and twelve x87 settings, plus
branches, nested calls, tracing, error exits and 256 mixed overlapping arithmetic
sequences per x87 setting. Comparisons include entire fixture globals/edicts,
function/profile counters, error/stack state and FPU CW/TOP/tag. The reusable
benchmark-suite fixture independently reproduced this pass from source.

The isolated full BENCH486 build passed complete i486 auditing: 316,258 relocated
instructions, 529 startup rows and 9,207 provider instructions, zero above-target,
unknown or exempt instructions.

## Independent gameplay timing

Three alternating pairs per map/device configuration measure 256 live-server
frames after 64 warm-up frames, with fixed simulation advancement from startup,
god mode, forward movement and firing. All captures are uninstrumented BENCH486,
VGA 320x200, the same pinned DOSBox-X 486/x87 environment and the same PAKs.

| Workload | Control median FPS | Candidate median FPS | FPS change |
|---|---:|---:|---:|
| e1m1, silent | 23.503420 | 23.536090 | +0.139001% |
| e1m2, silent | 21.868417 | 21.900981 | +0.148910% |
| e1m1, sound | 23.071491 | 23.103400 | +0.138305% |
| e1m2, sound | 21.200305 | 21.231525 | +0.147261% |

All 24 captures match final framebuffer/selected numeric simulation checksums and
the complete per-function QuakeC statement-count CSV within their configuration.
Pooling all twelve samples per variant gives 22.372902 -> 22.405018 FPS,
**+0.143550%**. The scripted population is not a claim about every combat/map load.

## Evidence and decision

Promote the opcode-specific work reduction subject to the combined integration
record. Profiling capability remains intact. This is one accepted optimization
attempt, not one per opcode or benchmark repetition. Emulator timing does not
establish real 486 cache-miss rates or physical-hardware FPS.

Workspace-relative evidence is `benchmarks/out/qc-operands-validation-20261108/`.
The source-built reusable test is
`benchmarks/out/qc-interpreter-reusable-validation-20261108/`, generated by the
benchmark suite's `tools/verify-qc-interpreter.py`. The final combined build/runtime
record is in that suite's `docs/I486-OPTIMIZATION-20261108.md`. That record separates
independent measurements from integration checks and records the final artifact.
